# LynxSecure / Quest-V：没有中央调度器的分离

<CORE RULE>
这两个系统的共同点是**极端的静态分离**，而且**都没有"中央调度器/中央管理内核"**：

```
没有大量 VM-exit
没有集中的设备分配代码
  → 不能证明"没有虚拟化隔离"
  → 很可能是"本来就不这么做"
```

LynxSecure 靠**静态配置**；Quest-V 靠**多内核 sandbox + 每 sandbox 一个 monitor**。**两条路都让"常规 hypervisor 应该有的东西"看起来缺失。**
</CORE RULE>

## 一、LynxSecure：静态配置 + 无中央管理

- 裸金属分离内核 hypervisor，按需把硬件资源（**CPU 核、内存、I/O**）分区给应用
- **静态配置 + 固定资源分配 + 精确的任务控制，"没有隐藏的调度器或干扰"**
- **应用与 CPU 之间没有中央管理内核**——应用获得**直接的 CPU 访问**；采用硬件强制的分离，**没有共享内存、没有集中调度**
- 安全基础是安全启动与密码学信任根，内核footprint 极小；可承载 Windows/Linux/Solaris 等 guest OS

**推论**：

```
runtime 里找不到"重配置 MMU / 设备分配"的完整管理代码
  → 与静态配置的模型自洽
  → 不是被 strip 掉
```

## 二、Quest-V：多内核 sandbox + 每 sandbox 一个 monitor

- 不是单一 hypervisor，而是**多个 sandbox kernel**，各自位于**独立的物理内存区域**，拥有**一部分核与 I/O 设备**；一个 sandbox 的故障不影响其他
- **每个 sandbox 有自己的 monitor**（用"每 sandbox 一个 monitor"替代"一个中央 hypervisor"）；monitor 只为**一个** sandbox 维护 EPT 映射，省去调度/切换 guest 地址空间的开销
- **monitor 只在必要时介入**：引导、故障恢复、建立 sandbox 间通信通道、初始化影子页表
- **sandbox kernel 自己做调度与 I/O 管理**；**设备中断直接投递给 sandbox kernel，无需 monitor 干预**
- sandbox 间通信：基于**共享内存**通道的消息传递原语，由 monitor 更新 EPT 映射来建立**私有**通道；跨 sandbox 通信使用**显式内存通道 + IPI**（本地 APIC 产生 IPI 与本地定时器事件）

**两个关键的"异常"**：

1. **没有大量 VM-exit** 是设计使然（sandbox 自己管 I/O）
2. **没有全局时钟**：每个 sandbox 有自己的物理时钟，事件计时由**每核本地定时器**管理，**不保证同步**；既没有全局时钟也没有全局调度器，跨 sandbox 的时序比较不能用单一时间线（相关研究为此专门推导了含时钟偏差的通信界限）

## 三、LynxSecure 的官方表述（用它判断"缺什么算正常"）

- **boot 时定义、不可变的硬件分区**；**不可变的硬件强制隔离**，从加电到断电持续保持
- **最小特权**：内核空间功能有限——**资源分区、控制分区之间的数据流、调解对系统状态变更函数的访问**
- **按开发者要求，把 I/O 与应用支持全部导出到用户态 guest**——内核里没有驱动、I/O 栈与应用 API
- 运行期约束（官方列举）：**没有 hypervisor/管理控制台登录**、**没有动态系统修改**、一个 guest 不能访问另一个 guest 的资源、**hypervisor 自身也不能访问 guest 的资源**、可 DMA 设备不能访问 guest 资源

**所以**：

```
运行态找不到完整的"VM 配置器 / 动态 MMU 配置引擎"
  → 与该模型自洽（静态配置 + 无动态系统修改 + 无管理登录）
  → 不要得出"固件被裁剪 / 被破坏"
```

（说明：公开资料**未直接证实**"用于初始配置的特权 setup code 随后被丢弃"这一具体机制；上面列的是官方明确表述的部分——判断"缺什么算正常"用它们即可。）

## 决策树

```
拿到 LynxSecure / Quest-V 一类目标
├─ 找不到集中管理/重配置代码
│    ├─ LynxSecure：静态配置 + 无中央管理内核 → 自洽
│    └─ 别判"代码被裁剪/被 strip"
├─ VM-exit 很少
│    ├─ Quest-V：sandbox kernel 自己管 I/O，设备中断直接投递
│    └─ 不能据此断定"没有隔离"
├─ 跨域通信
│    ├─ LynxSecure：无共享内存（硬件强制分离）
│    └─ Quest-V：显式共享内存通道 + IPI（monitor 建立私有通道）
├─ 时间线对不上
│    └─ Quest-V 无全局时钟：各 sandbox 时钟不保证同步，别按单一时间线比较
└─ 隔离边界
     ├─ LynxSecure：静态配置规定 CPU/内存/I/O 归属
     └─ Quest-V：每 sandbox 独立物理内存区 + 各自的 monitor 维护 EPT
```

## 工具与验证

- 配置/资源归属：静态配置（LynxSecure）或 sandbox 到核/内存/设备的映射（Quest-V）
- monitor/管理代码的存在范围：Quest-V 中 monitor 只在引导、故障恢复、建立通道、初始化影子页表时介入
- 时间：是否存在全局时钟（Quest-V 没有，用本地定时器与 TSC）
- 验证：能同时说清「资源由谁静态规定 + 哪些动作不需要管理代码参与 + 时序比较是否跨 sandbox」

## 该平台的坑（汇总）

- **把"缺少集中管理代码"当代码被裁剪**：静态配置模型本来就如此
- **把"VM-exit 很少"当没有虚拟化隔离**：sandbox 自己调度与管 I/O
- **在 LynxSecure 里找共享内存通信**：设计上是无共享内存、硬件强制分离
- **在 Quest-V 里期待中央调度器**：不存在，各 sandbox 自行调度
- **把不同 sandbox 的时间戳按单一时间线比较**：各时钟不保证同步
- **以为 monitor 参与每次 I/O**：它只处理引导、故障、通道建立与影子页表初始化
- **忽略"每个 sandbox 一个 monitor"的结构**：不是"一个 hypervisor 管所有"
