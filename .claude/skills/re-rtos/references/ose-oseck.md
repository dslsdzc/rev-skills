# OSE / OSEck：消息式 IPC 跨节点 / 动态代码更新

<CORE RULE>
OSE 系列的定位是**电信/分布式 RTOS**，其 IPC 模型与 POSIX 完全不同：

```
"signal" / "message" 不是 POSIX 信号
  → 它是消息对象，可以跨 core / CPU / DSP / node 传递
```

所以：

```
Process A 给 B 发"signal"
  → 不能自动按 POSIX signal 语义解释
```
</CORE RULE>

## 一、消息式 IPC 与 LINX

- OSE 家族（含 OSEck 紧凑版）共享**同一套消息式 IPC 框架与 API**
- **LINX** 是分布式透明传输层，**统一核内、处理器间、板间的通信**，支持多种物理介质：**共享内存、DMA、RapidIO/SRIO、以太网、PCI** 等
- 多核/DSP 节点上的应用**可以像在单核上一样交互**；新增节点对既有代码影响很小
- **零拷贝共享内存传输**是该家族公开强调的特性
- OSE 的直接消息传递模型中**消息所有权不共享**，避免内存访问冲突

**RE 含义**：

- trace 里看到的"消息传递"可能是**跨节点**的——本地看不到对端进程很正常
- 跨节点的通信路径可能**不产生任何本地 syscall**：它可能走共享内存/DMA/串行互连

## 二、动态代码与更新

- 公开资料表明 OSE 支持**动态代码更新/加载**；平台级的工具负责 DSP/CPU 阵列的加载、复位、日志收集与核心转储
- 因此"**模块被替换而系统继续运行**"在这一族里可以是正常设计

（说明：OSE 的 XIP（原地执行）能力在本次核验的公开资料中**未获证实**，分析时不要直接断言。）

## 决策树

```
拿到 OSE / OSEck 目标
├─ 看到信号/消息
│    ├─ 按"消息对象"解释，不是 POSIX signal
│    └─ 可能是跨 core / CPU / DSP / node 的
├─ 通信对端找不到
│    ├─ 可能在另一个节点上（LINX 对上层透明）
│    └─ 传输可能走共享内存/DMA/互连，不产生本地 syscall
├─ 数据路径性能异常
│    └─ 查是否走了零拷贝共享内存路径
└─ 模块/代码在运行中被替换
     └─ 动态更新是该族的既有能力，别先判劫持
```

## 工具与验证

- 通信：消息对象的所有者与对端；LINX 的介质选择（共享内存 / DMA / 互连）
- 拓扑：核内 / 处理器间 / 板间的分布；节点数量变化
- 生命周期：动态加载/更新点与平台级加载工具的行为
- 验证：能同时说清「这条消息是本地还是跨节点 + 走哪种介质 + 是否零拷贝路径」

## 该平台的坑（汇总）

- **把消息或 "signal" 当 POSIX 信号**：它是消息对象
- **以为通信对端一定在本地**：LINX 是分布式透明的
- **在本地 syscall trace 里找跨节点通信**：可能完全不经本地 syscall
- **按"消息所有权共享"理解数据流**：直接消息传递模型不共享所有权
- **把运行期代码替换当劫持**：动态更新是该族能力
- **断言其支持 XIP**：本次核验未证实，不要照搬
