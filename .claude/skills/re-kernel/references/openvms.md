# OpenVMS：AST / $QIO / 异步完成流

<CORE RULE>
OpenVMS 最特殊的逆向机制是 **AST（Asynchronous System Trap）**——一条**异步控制流**：

```
正常执行
  ↓ 外部事件（I/O 完成、定时器…）
AST 例程
  ↓ 返回
恢复原执行点
```

所以 **AST 例程可以没有任何普通 call xref**；把异步完成图当成同步调用图看，会得出"这些代码没人调用"的错误结论。
</CORE RULE>

## 一、$QIO 与事件标志

`SYS$QIO` 的关键参数：

| 参数 | 作用 |
|---|---|
| `efn` | 完成时**置位**的事件标志号 |
| `astadr` | 完成时执行的 **AST 例程地址** |
| `astprm` | 传给 AST 例程的参数 |
| `chan` / `func` | 通道与功能码 |
| `iosb` | 接收最终状态的 I/O 状态块 |

- **发起时事件标志会被清除**（所有异步系统调用都如此）；完成时置位
- `iosb` 技术上可选，但**不应当作可选**——并发的异步事件要各用一个独立的 IOSB

## 二、完成顺序（控制流）

```
① 写 IOSB   →   ② 置事件标志   →   ③ 触发 AST
```

- 指定了 `astadr` 时，系统在 I/O 完成时**中断进程并把控制交给 AST 服务例程**；例程结束时**控制返回到被中断的那个点**
- 指定 `astadr` 时应同时指定 `iosb`，好让 AST 能判断完成状态

## 三、事件标志不等于"这个 I/O 完成"

- 等待服务（`$WAITFR`/`$WFLOR`/`$WFLAND`）等的是**标志**，不是 I/O——别的操作也可能置位同一标志，所以标志用法必须协调
- 测试异步完成推荐用 **`SYS$SYNCH`**（同一 `efn` + IOSB）：置位后检查 IOSB，**IOSB 非零表示操作已完成；为零则清标志再等**
- **`W` 后缀 = 同步版本**（`$QIO/$QIOW`、`$GETJPI/$GETJPIW`、`$ENQ/$ENQW`）
- 只有在**该标志上没有未完成的异步变化**时清除标志才合适

## 四、AST 的语义（决定了"为什么这个等待会重新开始"）

- AST 像子程序调用，但**无视主流程上下文异步投递**；主线与 AST 共享的代码**必须可重入**，共享数据在临界区要被屏蔽 AST 保护（或用原子序列）
- **AST 不会中止进行中的系统调用**
- 进程 `$HIBER` 或在 `$WAITFR` 上等待时：AST 投递会**把进程暂时移出等待**去执行 AST，AST 完成后**原来的等待调用会被再次执行**（等待理由被重新评估）
  - 除进程删除外，跳出这个循环的唯一方式是 `$WAKE` 或 `$SETEF`
- **所以**：`wait 看起来"返回后又自动等待"不是 loop corruption**，是这个模型的正常行为
- 同一访问模式下，AST 例程**不能被同访问模式的另一个 AST 抢占**，但**可以被更高访问模式的 AST 抢占**（如执行模式 AST 抢占用户模式 AST）
- **特殊内核模式 AST（Special Kernel-Mode AST）** 是获得进程上下文的标准机制：在下一次该进程被调度时以该进程最高优先级执行

## 五、屏蔽 AST

- `$SETAST` 可关闭/开启**当前及所有更低特权访问模式**的 AST 投递
- 极短临界区可用**每进程 P1 空间里的两个标志位**代替 `$SETAST`，避免其开销：内核 AST 投递代码置"AST 已禁用"位，若第一位已置则再置第二位并**不投递**该 AST；用户代码事后检查第二位并调用 `$SETAST` 重新开启

## 决策树

```
拿到 OpenVMS 目标
├─ 某个例程没有任何调用者
│    ├─ 查它是否作为 astadr 传给 $QIO / 定时器 / 其他异步服务
│    └─ 别判死代码
├─ 完成路径不完整
│    ├─ 补上 AST 边：$QIO → (IOSB → 事件标志 → AST) → 业务逻辑
│    └─ 注意完成顺序：写 IOSB → 置标志 → 触发 AST
├─ 等待"返回后又继续等待"
│    └─ AST 投递后原等待被重新执行，属正常
├─ 事件标志被置位但数据没到
│    └─ 标志不等于该 I/O 完成；用 $SYNCH + IOSB 判定
└─ 共享数据异常
     └─ 检查是否用 $SETAST 或 P1 标志位做了 AST 屏蔽，以及代码是否可重入
```

## 工具与验证

- 异步登记点：`$QIO` 等服务的 `astadr`/`astprm`/`efn`/`iosb` 参数
- 完成判定：`$SYNCH` 的用法与 IOSB 含义；`W` 后缀同步版本的存在
- 屏蔽：`$SETAST` 调用点与 P1 空间标志位的使用
- 验证：能同时说清「这条 I/O 是同步还是异步 + 完成时经哪条 AST 边回到业务 + 该 AST 是否可被抢占/被屏蔽」

## 该平台的坑（汇总）

- **把 AST 例程当无调用者的死代码**：它由异步事件驱动
- **用同步调用图解释完成路径**：必须补 AST 边
- **把"等待返回后又自动等待"当循环被破坏**：AST 投递后原等待会被重新执行
- **把事件标志置位当该 I/O 完成**：标志可能被别的操作置位；用 `$SYNCH` + IOSB 判定
- **忽略 IOSB**：并发异步事件必须各用一个 IOSB
- **以为 AST 会中止正在进行的系统调用**：不会
- **在主线与 AST 间共享数据却不做屏蔽/原子**：AST 异步投递，必须可重入
- **忽略 `$SETAST` 与 P1 标志位两种屏蔽方式**：短临界区的实现与常规不同
