# IBM i：单一存储层 / 对象式寻址

<CORE RULE>
IBM i 最特殊的机制是 **single-level storage（单级存储）**：

```
主存（RAM）与辅存（磁盘）不被区分
内存 + 磁盘 = 单一 64 位地址空间
```

于是：

```
object address
  ≠ 「当前由 DRAM 支撑的指针」
```

做存储/对象生命周期分析时，**先恢复 IBM i 的对象与存储抽象，而不是套 POSIX 文件模型**。
</CORE RULE>

## 一、单一存储层怎么工作

- 系统把**全部存储视为一个整体**，不区分主存与辅存；**内存与磁盘共同构成一个 64 位地址空间**（1991 年起 64 位；此前为 48 位）
- 由 Licensed Internal Code（LIC）**隐藏物理磁盘**并管理其上的对象存储：**在一个覆盖磁盘空间的虚拟地址空间上寻址对象，而不是用盘号/柱面/扇区**
- 程序需要的对象从"磁盘上的地址空间"被**分页调入**主存地址空间；页可能驻留在 RAM 或磁盘上，由操作系统按需定位

## 二、对象式寻址

- 任何可执行代码或数据都封装为**对象**（object）；系统上的一切都是对象，**库也是对象**（且是其他对象的容器）
- 因为是单一地址空间，**对象按名字访问而不是按硬件地址**，与其物理位置无关（这同时提供完整性）
- 对象用**限定名**标识（`库/对象`）；**指针是全局的**，因此程序之间共享数据很方便
- 默认情况下操作系统与应用**只看到一个大虚拟存储池**（system ASP，永远是 ASP 1），而不是物理驱动器；增加磁盘会自动扩展它

## 三、可观察到的后果

- **对象的数据分散在所有物理盘上**（LIC 透明处理），支持并行磁盘 I/O，同一个对象可同时被多个盘臂访问；不存在"某个盘满了"或碎片化问题
- **任务切换非常快**——只是一条分支指令，不需要创建独立地址空间
- 数据库对象与应用共享同一内存；可以通过虚拟地址透明访问缓存数据，I/O 可被异步调度

## 决策树

```
拿到 IBM i 目标
├─ 看到"地址"
│    ├─ 先问：这是对象地址还是主存地址
│    └─ 内存与磁盘同处一个 64 位地址空间，别假设它由 DRAM 支撑
├─ 对象与引用
│    ├─ 按限定名（库/对象）与全局指针恢复引用关系
│    └─ 不要套 POSIX 文件/inode 模型
├─ 存储布局相关
│    └─ 物理盘被 LIC 隐藏；对象跨盘分散，没有"盘号"概念
└─ 性能/时序分析
     └─ 任务切换是分支级别的，不能按普通进程切换成本估算
```

## 工具与验证

- 对象：限定名、对象类型、库（容器）层级
- 存储：单一地址空间的寻址方式；分页调入的行为
- 验证：能同时说清「这个引用是对象引用还是主存地址 + 它属于哪个库 + 页面当前在内存还是磁盘」

## 该平台的坑（汇总）

- **把对象地址当 DRAM 支撑的指针**：内存与磁盘是一个地址空间
- **用盘号/柱面/扇区理解存储**：物理磁盘被 LIC 隐藏
- **套 POSIX 文件模型恢复引用关系**：应是对象 + 限定名 + 全局指针
- **以为库只是目录**：库本身也是对象、是容器对象
- **按普通进程切换成本估算任务切换**：它只是分支指令
- **假设对象连续存放**：对象跨物理盘分散
